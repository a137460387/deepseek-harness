# Agent Note: 历史召回让位于用户已编辑的草稿

Status: implemented

[English](2026-08-21-input-history-recall-edit-takeover.md) | 中文

## Problem

一旦 ArrowUp/ArrowDown 历史遍历进入活跃状态,后续每一次方向键都会被无条件认领:插件不管用户在此期间做过什么,都把整段草稿替换为下一条历史。召回一条消息、点进召回文本里编辑的用户,会在下一次按方向键时丢失编辑——草稿被整体替换,而且编辑永远不会进入 stash(stash 只保存进入遍历前的草稿)。遍历原有四个出口(会话切换、草稿清空、ArrowDown 翻过最新一条、fiber 销毁),唯独没有"用户已接管编辑"。

原始设计有意在遍历中跳过光标复查(功能 note 的细化第 2 条):`setDraft` 之后 React 受控重渲染把光标放在引擎决定的位置,插件无法稳定观测。该理由只覆盖"紧跟插件写入的那一次按键",对"紧跟*用户*编辑的那一次按键"只字未提——那一刻草稿内容正是用户留下的样子,完全可观测——但实现把这个豁免静默地延伸到了该情形。功能 note、README、代码注释、测试里都没有记录这一后果;它是实现缺口,不是决策。

## Decision

遍历槽(`RecallSlot`)现在记录 `written`——插件最近一次写入草稿的文本:以进入时的草稿做种子(首次历史写入发生在打开遍历的同一按键内),并在每次遍历写入时更新。keydown 处理器里,紧跟现有的空草稿重置、位于 ArrowUp/ArrowDown 分支之前,新增一个检查:活草稿不再匹配 `written` 时结束遍历:

- 不匹配检查是纯字符串比较。编辑后改回与写入文本完全一致则遍历继续——这是有意的简化,不做脏值追踪。
- 结束遍历的同时把触发按键交还(`return`,不认领):对一个刚打完字的用户,覆写其编辑或仅仅吞掉按键,任何一种都会造成意外。
- 空草稿重置保持在编辑检查之前、保持既有语义(重置后继续处理该次按键):草稿清空意味着发送,而"发送后立即按 ArrowUp"必须仍能经光标在第 0 位的门槛召回最新一条——提前 return 的形态会破坏这条路径。
- 该检查位于 IME/焦点/会话/phase/菜单守卫之后,因此会被这些守卫忽略的按键不会改动遍历状态(按进打开的候选菜单的方向键不得结束遍历)。

这与被跳过的光标复查是不同维度,代码注释也写明了:插件写入后的光标由引擎放置、不可稳定观测,但写入的*内容*精确已知,任何分歧都是用户自己的编辑。前者豁免的是不可观测之物;本检查针对的是可观测之物。

## Testing

`packages/extensions/input-history-recall/tests/input-history-recall.client.spec.ts` 新增两个用例:用户编辑(经输入状态机写入,绕过插件的 `setDraft` 路径)后,下一次 ArrowUp 放行且不认领、编辑保持原样、遍历已结束(随后的 ArrowDown 也放行);编辑后改回与写入文本完全一致则遍历继续(下一次 ArrowUp 仍向更早翻)。33 个既有用例——含不编辑的多次按键往返——原样通过,钉住了最常见的无编辑路径未被触碰。

## Alternatives considered

**监听 `selectionchange` 或输入事件做接管检测。** 为草稿比较已能提供的信号引入自带生命周期与清理负担的监听器;还会在用户并无接管意图的光标移动上触发。

**把单纯的光标移动当作接管。** 点击到召回文本中间阅读并不意味着用户想要回方向键;内容变化才是诚实的信号。

**编辑时结束遍历但仍处理触发按键。** 会落回本 bug 制造的同款双重意外:编辑后的那次按键仍会认领或改写。

**把该检查折叠进空草稿重置。** 两个重置对触发按键的处理不同(继续处理 vs 交还);合并会破坏空草稿重置支持的"发送后立即召回"路径。

**用脏值追踪替代字符串相等。** 能区分"改走又改回"与"从未编辑",代价是第二份遍历状态;这一区分对该手势没有任何可观测收益。

## Consequences

活跃遍历现在被用户自己的编辑所约束:草稿一旦偏离插件所写,召回即让位,方向键回到原生行为,直到光标在第 0 位的门槛重新打开一次遍历。stash 语义不变(仍保存进入遍历前的草稿),因此"编辑后有意经 ArrowUp 重新进入"会把*编辑后的*草稿存入 stash。"改回原样"的角落(打字又撤销回写入文本)保持遍历存活——作为纯字符串比较的已接受产物。
